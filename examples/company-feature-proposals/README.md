# Company feature proposal test pack

Ten synthetic business proposals grounded in real software and crypto companies. The set includes five companies with documented commercial scale and five with historical business failure or shutdown; those outcomes are recorded separately from the proposal inputs.

These are authored test inputs, not authentic company proposals, captured Idea Autopsy runs, or validated business recommendations. No proposal has been evaluated by the plugin as part of creating this pack.

## What is real and what is invented

- Source-linked product context is drawn from primary sources checked September 22, 2026. Citations in an input are claims with provenance, not proof that a reviewing agent has independently verified them.
- Every proposed feature, internal observation, participant commitment, balance sheet, budget, forecast, staffing allocation, and experiment is fictional. An observation explicitly supplied in a fixture can support conditional reasoning within that scenario; it is never actual company evidence.
- Referenced interview logs, datasets, and test suites are summarized scenario premises, not hidden attachments or executable artifacts. Do not invent individual records, quotations, or test results beyond what the input provides.
- Features may overlap existing or past products. The pack makes no exhaustive novelty claim.
- Failed-company cases are counterfactual operating-era scenarios written with retrospective knowledge. They are not present-day launch proposals or strict historical backtests. Current help documents are not backdated.
- Real names remain visible by choice. Hiding the outcome key reduces explicit answer leakage but does not remove a model's prior knowledge of the companies.

## How to use the pack

1. Start a fresh evaluation context for each case. Supply only the chosen numbered proposal as source and use its stated commitment as the decision context.
2. Keep this index, [SOURCES.md](SOURCES.md), and [EVALUATION-NOTES.md](EVALUATION-NOTES.md) out of the evaluator's initial input. The latter two are provenance and scoring aids, not additional proposal evidence.
3. Run closed-world first. If separately authorized, run claim verification as a distinct condition and record which external sources it adds. Source links must not silently authorize browsing.
4. Ask for consequential choices or missing facts when needed. A user or test operator supplies answers, not a replacement proposal; the agent writes revisions and a change record. Preserve unanswered questions and do not manufacture experiment results.
5. Save run outputs outside this source directory. Preserve the original, source hash, versions, findings, answers, assessment status, and coverage. Compare the run with the evaluator notes only afterward.

Run one case or a separately authorized batch; creating these fixtures does not authorize evaluations, recruitment, experiments, spending, publication, or actions at the named companies. No fixed business verdict is encoded in this pack.

## Coverage and limits

The proposals intentionally vary in evidence, arithmetic, requested authority, and readiness. Deliberately misleading calculations remain in the inputs and are explained in the evaluator notes. Several contain useful assets alongside serious flaws. Some ask only for learning; others request a launch their evidence may not support.

Use the pack to inspect provenance discipline, causal issue counting, commitment-scoped judgment, consequential questions, and agent-written revision. It does not establish statistical evaluation performance or substitute for real customer research. Structural checks and repository unit tests do not measure the quality of model judgments on these proposals.
